# Vercel filters the `Server-Timing` response header

Status: reproducible in production  
Observed: July 21, 2026  
Project: `ashirsc/finstream`  
Production domain: `https://finstream.hirschi.dev`

## Summary

Vercel silently removes the standard HTTP `Server-Timing` response header.
The behavior applies both to responses generated by a Vercel Function and to a
static asset whose header is configured directly in `vercel.json`.

An adjacent custom response header is forwarded correctly. This isolates the
behavior to the header name rather than the application, response source, or
general custom-header handling.

Vercel's response-header and `vercel.json` documentation does not currently
identify `Server-Timing` as reserved, unsupported, or filtered:

- https://vercel.com/docs/headers/response-headers
- https://vercel.com/docs/project-configuration/vercel-json#headers

## Expected behavior

Vercel should forward a valid `Server-Timing` response header so browsers can
display application metrics in the Network panel and expose them through the
Performance API.

Example:

```http
Server-Timing: db;dur=24.8, handler;dur=31.2, total;dur=31.5
```

If Vercel intentionally reserves this header, the restriction and supported
alternatives should be documented.

## Actual behavior

Vercel returns the response without `Server-Timing`. Other response headers,
including a custom header containing the identical value, are preserved.

This is visible with `curl`, so it is not Chrome or browser DevTools removing
the header.

## Static edge reproduction

The repository contains a static file at:

```text
public/static/server-timing-probe-20260721.txt
```

The following rule adds a cache policy, a custom control header, and
`Server-Timing` to the same response:

```json
{
  "source": "/static/server-timing-probe-20260721.txt",
  "headers": [
    {
      "key": "Cache-Control",
      "value": "private, no-store"
    },
    {
      "key": "X-Server-Timing-Probe",
      "value": "control-present"
    },
    {
      "key": "Server-Timing",
      "value": "edge-probe;dur=1.0"
    }
  ]
}
```

Reproduce with:

```sh
curl -sS -D - -o /dev/null \
  https://finstream.hirschi.dev/static/server-timing-probe-20260721.txt
```

The first request after deploying the new, never-requested path returned:

```http
HTTP/2 200
age: 0
cache-control: private, no-store
content-type: text/plain; charset=utf-8
x-server-timing-probe: control-present
x-vercel-cache: MISS
x-vercel-id: sfo1::dlkr8-1784658522411-9bd1624b2634
```

`Server-Timing` was absent. This response was a cache miss with an age of zero,
while Vercel forwarded the adjacent control header. The static response was
served at the edge, as expected; its `x-vercel-id` therefore does not include
the function region.

## Function reproduction

The application emits the standard header through NextRS/Axum and mirrors the
exact value to `x-debug-server-timing` immediately before converting the Axum
response for the Vercel runtime.

Relevant response middleware:

```rust
async fn mirror_server_timing(request: Request, next: Next) -> Response {
    let mut response = next.run(request).await;
    if let Some(value) = response.headers().get(SERVER_TIMING).cloned() {
        response.headers_mut().insert(DEBUG_SERVER_TIMING, value);
    }
    response
}
```

Reproduce an unauthenticated function response with:

```sh
curl -sS -D - -o /dev/null \
  'https://finstream.hirschi.dev/login?server_timing_probe=20260721'
```

Observed response headers:

```http
HTTP/2 200
cache-control: private, no-store
content-type: text/html; charset=utf-8
x-debug-server-timing: mw;dur=0.0, handler;dur=0.0, total;dur=0.0, route;desc="/login"
x-vercel-cache: MISS
x-vercel-id: sfo1::pdx1::59tmw-1784658522872-784cb761510d
```

The `sfo1::pdx1` identifier confirms that this request traversed the edge and
executed in the configured `pdx1` function region. The custom mirror arrived,
but the original `Server-Timing` header did not.

## Causes ruled out

The two reproductions rule out:

- Chrome or browser DevTools: the header is also absent in `curl`.
- NextRS timing generation: the generated value reaches the mirror middleware.
- Axum response handling: the custom mirror is added to the same response.
- The custom NextRS streaming adapter: it preserves the original response
  status and headers when changing the body type.
- `vercel_runtime`: it passes the Hyper response through without filtering this
  header.
- Function response streaming: the static edge reproduction has no function or
  streaming adapter.
- Cached content: the static evidence was captured on a cache miss with
  `age: 0` and `private, no-store`.
- General custom-header configuration: `X-Server-Timing-Probe` from the same
  `vercel.json` rule is present.

The remaining common boundary is Vercel's platform response processing.

## Current workaround

Production mirrors the value to:

```http
X-Debug-Server-Timing: db;dur=24.8, handler;dur=31.2, total;dur=31.5
```

This preserves the diagnostic data for `curl` and the Network panel's response
headers. It does not receive the browser's native `Server-Timing` parsing or
Timing-panel visualization.

Other possible workarounds are placing a proxy in front of Vercel that converts
the custom header back to `Server-Timing`, or hosting the function on a platform
that forwards the standard header. Both add operational complexity and should
be unnecessary if the filtering is a platform bug.

## Vercel report template

### Title

Vercel silently strips the standard `Server-Timing` response header

### Description

Vercel removes `Server-Timing` from production responses without documenting
the header as reserved or unsupported.

We reproduced this through two independent paths:

1. A Vercel Function emits `Server-Timing` and mirrors the identical value to
   `x-debug-server-timing`. The public response includes the custom mirror but
   not `Server-Timing`. Its `x-vercel-id` includes `pdx1`, confirming function
   execution.
2. A true static asset receives `Server-Timing` and a custom control header from
   the same `vercel.json` rule. On the first request, the response had `age: 0`,
   `x-vercel-cache: MISS`, and `cache-control: private, no-store`. Vercel
   forwarded the control header and removed `Server-Timing`.

Static reproduction:

```sh
curl -sS -D - -o /dev/null \
  https://finstream.hirschi.dev/static/server-timing-probe-20260721.txt
```

Expected: Vercel forwards `Server-Timing: edge-probe;dur=1.0`.

Actual: the header is absent, while
`X-Server-Timing-Probe: control-present` is present.

Is this intentional? If so, please document the restriction and a supported
way to expose standard server timing metrics. If not, please remove the
platform filtering.
